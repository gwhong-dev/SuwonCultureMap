**한눈에 보기**
- 하려는 일: 재단 API에 없는 행사(인스타에만 올라오는 행사)를 같은 지도에 추가
- 방식: 공식 API로 게시물 조회 → 캡션 정리(규칙 기반 파서가 먼저, 못 읽는 것만 AI) → 카카오 장소 검색으로 좌표 → 저장 → 지도 표시

- 캡션 실물 확인(2026-10-31): 한 글에 행사가 20개 이상인 월간 모음, 날짜 줄이 있는 공지, 스포츠 · 기념식 혼재 → 3-1에 정리하고 "여러 행사 글 처리 · 올릴 범위 · 규칙 기반 우선"을 8번에서 결정

## 1. 목적과 원칙

| 원칙 | 이유 |
|---|---|
| 크롤링(자동 긁기) 안 함, 공식 API만 | 약관 위반 위험 · 계정 차단 |
| 사진은 복사하지 않고 원본 링크(`permalink`)만 보관 | 저작권 |
| 못 읽으면(규칙 · AI 모두) **비워 둔다**(null) | 틀린 값을 넣는 것보다 낫다 (캘린더 B안과 같은 원칙, PR #23) |
| 정리 결과(규칙 · AI 모두)는 **코드가 다시 검증**하고, 통과한 것만 지도에 올린다 | 파서 · AI 출력을 그대로 믿지 않는다 |
| 토큰 · 키는 환경변수로만 | 커밋 금지 (`CLAUDE.md` §4) |
| 실제 게시물 캡션을 저장소에 커밋하지 않음 | 위 저작권 원칙. 테스트 샘플은 직접 만든 가상 캡션 |

## 2. 파이프라인 (5단계)

| 단계 | 하는 일 | 입력 → 출력 | 실패하면 |
|---|---|---|---|
| ① 수집 | 공식 API(Business Discovery = 다른 계정의 공개 게시물 조회 기능)로 대상 계정의 최근 게시물 조회 | 계정명 → 게시물(`id`, `caption`, `permalink`, `timestamp`) | 그 계정만 건너뛰고 로그, 다음 계정 진행 |
| ② 정리 | 캡션을 **행사 블록으로 나눈 뒤**(한 글에 행사가 여러 개일 수 있음, 3-1) 규칙 기반 파서가 먼저 읽고, 못 읽는 블록만 AI가 정리 | `caption` → 블록마다 `{행사 여부, 제목, 카테고리, 시작일, 종료일, 시간 원문, 장소명}` | 형식이 틀리면 `FAILED`로 기록, 지도 제외. 모음 글인데 블록을 못 나누면 `FAILED`(이유 기록) |
| ③ 좌표 | 카카오 장소(키워드) 검색으로 장소명 → 좌표 | 장소명 → 위도·경도 | 못 찾으면 `NO_COORD`(보류), 지도 제외 |
| ④ 저장 | 게시물 `id` + 블록 키 기준으로 중복 없이 저장 · 갱신 ((제안) 블록 키는 글 안 순서가 아니라 제목 + 시작일 + 장소명 같은 값이 안전함 — 캡션이 수정되면 순서가 바뀌고, 같은 제목 · 날짜에 장소만 다른 블록이 있을 수 있음. 구현 때 확정하고, 키가 바뀐 옛 행은 7번 #13 대로 처리) | | 같은 키는 갱신 (재실행해도 중복 X) |
| ⑤ 표시 | 마커 + 상세 패널에 인스타 원문 링크 (임베드는 보조) | | 링크 버튼만 숨김 |

## 4. 데이터 모델 (결정 필요)

현재 `Event`는 `idx`(재단 원본 PK), `title`, `category`, 좌표, `pubDate`가 **NOT NULL**이고 `idx`는 unique이다 (`Event.java:27-60`). 그리고 찜(`Favorite`)은 `Event`의 PK(`event_id`)를 직접 가리킨다 (`Favorite.java:44`). 인스타 행사에는 재단 `idx`가 없다.

| 안 | 내용 | 장점 | 단점 |
|---|---|---|---|
| A | 별도 테이블 `instagram_event`, `/api/events` 응답에서 합쳐 내려줌 | `Event`를 안 건드림 | **찜이 안 붙음** (`Favorite`이 `Event`만 가리킴) |
| B | `Event`에 `source` · `sourceKey` 추가, `idx`를 nullable로 변경 | 한 곳에 모임, 찜 그대로 동작 | 이미 있는 NOT NULL을 푸는 변경이 `ddl-auto=update`(JPA가 테이블을 자동 변경하는 설정, Flyway 도입 전 운영 값)로는 안 될 가능성이 큼 → **Flyway**(DB 구조 변경을 파일로 관리하는 도구) 먼저 (PR #32) |
| C | `Event`에 `source` · `sourceKey` 추가, 인스타 행사의 `idx`는 임시 음수값 | 스키마 변경 최소 | 의미 없는 값이 unique 칸에 들어가 지저분함 (비추천) |

- 어느 안이든 **원본 게시물 처리 상태**는 별도 테이블 `instagram_post`에 둔다. 게시물 `id`를 unique로 해서 재실행해도 중복되지 않게 한다.
- 한 게시물에 행사가 여러 개일 수 있으므로(3-1) 처리 상태(`PARSED` · `NO_COORD` 등)는 게시물이 아니라 **블록(행사 후보) 단위**로 둔다. `instagram_post`(수집 상태) 아래에 블록 행을 두는 구조는 3번(데이터 모델) 작업에서 정한다.
- 처리 상태값: `PENDING`(수집됨) / `PARSED`(정리됨) / `NO_COORD`(좌표 못 찾아 보류) / `NO_DATE`(날짜를 못 읽어 보류 — 시작일 없음 · 일 없음 · 반복만 있는 블록, 지도 제외) / `NEEDS_REVIEW`(사람 확인 대기, 8번 5번을 택할 때만) / `READY`(지도 노출) / `FAILED`(형식 · 검사 실패) / `SKIPPED`(행사가 아니라고 판단한 블록 · 글)
- `Event`로 승격할 때 NOT NULL 칸 채우는 규칙: `category`는 파서(규칙 또는 AI)가 정한 값, 비면 `"기타"`(재단 `"전체"` → `"기타"` 처리와 같은 방식, `EventSyncService.java:65`) / `pubDate`는 게시물 `timestamp`를 한국 시간으로 변환
- **결정: B** (2026-10-31). 출처마다 표를 따로 두면 찜이 여러 표를 가리켜야 해서 DB가 연결을 지켜 주지 못하고(외래 키 불가), 찜 · 캘린더 · 지도 코드가 출처마다 반복됨 → 화면에 보이는 행사는 `Event` 한 표, 출처별 처리 상태만 따로(`instagram_post` 등). Flyway 도입(PR #32)이 먼저.
- `ddl-auto=update`가 기존 컬럼의 NOT NULL을 풀지 않는다는 점은 일반적으로 알려진 동작이며, 착수 때 실제로 확인한다.
- **Flyway V2 이후 작성 원칙** (PR #32 리뷰)
  - 기존 DB는 `ddl-auto=update`로 만들어져 unique · FK 이름이 Hibernate 자동 이름(`UK…` · `FK…`)이고, V1의 이름(`uk_event_idx` 등)은 빈 DB에서만 쓰임 → **V2에서 제약 이름을 직접 지정해 지우거나 바꾸지 않는다** (CI의 H2는 통과하고 사용자 DB에서만 실패함). 칸 단위 변경(`ALTER TABLE … MODIFY/ADD COLUMN`)으로 쓴다
  - 나중에 `nullable=false`를 붙인 칸은 기존 DB에서 NULL 허용으로 남아 있을 수 있음 → NOT NULL을 기대하는 V2는 쓰지 않거나 먼저 값을 채운다
  - 되돌리기: Community 판은 자동 되돌리기(undo)가 없음 → 위험한 V2는 되돌리는 SQL을 PR 본문에 같이 적는다. 급할 땐 내 PC `application-dev.properties`에 `spring.flyway.enabled=false`
  - 앱이 "표 없음"(validate 실패)으로 멈추면: 일부 표만 있는 DB가 baseline된 경우 → 그 DB를 비우고(데이터 백업 후) 다시 실행하면 V1부터 만들어짐
- 현재 동기화는 삭제 로직이 없어서 (`EventSyncService.java:78-103`) B안에서도 기존 재단 동기화가 인스타 행사를 지우지는 않는다.

## 5. 정리 단계의 약속 (규칙 기반 파서 + AI)

**입력:** `caption`(글) → 행사 블록으로 나눈 뒤 **블록 단위**로 처리. AI에는 못 읽은 블록의 원문만 넘긴다
**출력(JSON):** `isEvent` · `title` · `category` · `startDate` · `endDate` · `timeText` · `placeName` — 모르는 칸은 `null`. 한 글에 행사가 여러 개면 **블록마다 하나씩**(배열)
**`timestamp`의 용도:** `pubDate`를 채우고 정렬에 쓰는 것뿐이다. **연도를 추정하는 데는 쓰지 않는다** (UTC로 오므로 저장 때 한국 시간으로 변환).

코드가 규칙 · AI 출력을 받은 뒤 **다시 검사**한다 (출력을 그대로 믿지 않음).

| 검사 | 이유 |
|---|---|
| JSON 형식 · 허용된 칸만 | 엉뚱한 출력 방지 |
| 날짜 형식, 시작일 ≤ 종료일 | 잘못된 기간 방지 |
| 날짜가 **그 블록의 원문에 `M. D.` 꼴로 있는지** 대조 (캡션 전체가 아니라 블록 기준, 낱개 숫자 일치는 불인정) | AI가 없는 날짜를 지어내는 것(환각) 방지. 모음 글에서 다른 행사의 날짜와 우연히 맞는 경우를 막음 |
| 제목 · 장소 · 시간 길이 제한 | DB 칸 길이를 넘으면 저장이 실패할 수 있음 (PR #23 리뷰에서 지적되어 머지 전에 고친 위험) |
| `isEvent=false`(후기 · 광고 · 공지)인 블록 · 글은 `SKIPPED` | 행사가 아닌 글 제외 |

- 연도가 글에 없으면 **추측하지 않고 `null`**. 날짜가 `null`이면 `NO_DATE`로 두고 지도에 올리지 않는다. (같은 줄 시작일의 연도를 종료일에 쓰는 것은 추측이 아님 — 3-1)
- **규칙 기반 파서가 먼저** 읽는다 (`🗓️` · `📍` 같은 라벨 줄, `YYYY. M. D.(요일)` 날짜 형식). 못 읽거나 애매한 블록만 AI에 맡긴다. 날짜 줄이 있어도 행사가 아닌 공지가 있어(3-1) 행사 여부 판단은 규칙과 AI로 나눠 맡는다 — 세부 방법은 PR 1에서 정한다. 규칙이 읽은 값도 위 "다시 검사"를 똑같이 통과해야 한다.
- AI 호출은 인터페이스 뒤에 두고, 테스트에서는 **가짜 구현**을 쓴다.
- AI 공급자(Gemini 무료 한도 / Ollama 내 PC)는 **미결정** (8번). 클라우드 세션에서는 둘 다 쓸 수 없다고 가정하고, 실제 호출은 사용자 PC에서 확인한다.

## 6. 작업 순서 (한 PR = 한 목적)

| 순서 | 작업 | 키 필요 | 검증 |
|---|---|---|---|
| **0** | ✅ **Meta 사전 확인 (코드 없음) — 완료 2026-10-31.** 사용자 PC에서 Business Discovery 실호출(대상 1계정, 본인 앱 토큰) → `caption` 등 5개 필드 수신 확인. 권한 · 검수 · 약관은 3번 표에 남은 항목으로 정리 | ✔ Meta | 사용자 PC |
| 1 | 캡션 정리기 — 행사 블록 나누기 · 규칙 기반 파서 · AI 인터페이스(가짜 구현) · 출력 검증, 직접 만든 가상 캡션으로 단위 테스트 | ✗ | CI |
| 2 | ✅ 장소 → 좌표 (카카오 로컬 키워드 검색, 수원 범위 · 이름 확인, PR #31). 로그인에 쓰던 REST 키를 같이 씀. 카카오 개발자 콘솔에서 카카오맵 API가 켜져 있어야 함(2024-12부터, 사용자 PC 확인) | 운영에서 ✔ 카카오 REST 키 (테스트는 가짜 응답이라 ✗) | CI |
| 3 | 데이터 모델 (4번 결정 후, B안이면 Flyway 먼저) | ✗ | CI + 사용자 PC |
| 4 | ✅ 수집 클라이언트 (Business Discovery, PR #33 — 가짜 서버 테스트까지. 실제 호출 확인은 5단계) | ✔ Meta 토큰 | CI (실호출은 5단계 사용자 PC) |
| 5 | 저장 · 동기화 연결 (처리 상태 흐름) | ✔ | 사용자 PC |
| 6 | 지도 표시 (원문 링크, 임베드는 선택) | ✗ | 사용자 기기 |

0단계를 맨 앞에 두는 이유: 1~3번이 "`caption`이 온다"는 가정 위에 지어지는데, 그 가정이 4번에서야 확인되면 앞 작업을 다시 해야 할 수 있다.

0단계에서 못 끝낸 확인의 시점:
- **약관 확인은 3번(데이터 모델) 전에** 끝낸다. 저장하는 값의 범위가 약관에 따라 달라질 수 있기 때문이다.
- 장기 토큰 교환 · Live 모드 검수 여부 · 호출 제한은 5번(저장 · 동기화 연결)에서 확인한다 (4번은 PR #33 에서 가짜 서버 테스트까지만 — 실제 호출 경로가 5번에서 생기기 때문).
