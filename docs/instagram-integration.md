# 인스타그램 게시글 연동 — 설계 (초안)

> **상태: 설계 + 0단계(Meta 사전 확인) 완료 (코드 없음).** 구현은 "6. 작업 순서"대로 PR을 나눠 진행한다.
> **확인됨** = Meta 공식 문서에서 읽었거나 0단계 실호출로 확인한 것, **미확인** = 둘 다 못 한 것. 미확인 항목은 구현 착수 때 다시 확인한다.

**한눈에 보기**
- 하려는 일: 재단 API에 없는 행사(인스타에만 올라오는 행사)를 같은 지도에 추가
- 방식: 공식 API로 게시물 조회 → AI가 캡션 정리 → 카카오 장소 검색으로 좌표 → 저장 → 지도 표시
- 0단계 결과(2026-10-31): 실제 호출로 `caption`을 포함한 게시물 필드가 온다는 것을 확인. 남은 불확실성은 약관 · 장기 토큰 · 호출 제한 · Live 모드(일반 공개 상태) 검수 (3번 표)

## 1. 목적과 원칙

| 원칙 | 이유 |
|---|---|
| 크롤링(자동 긁기) 안 함, 공식 API만 | 약관 위반 위험 · 계정 차단 |
| 사진은 복사하지 않고 원본 링크(`permalink`)만 보관 | 저작권 |
| AI가 못 읽으면 **비워 둔다**(null) | 틀린 값을 넣는 것보다 낫다 (캘린더 B안과 같은 원칙, PR #23) |
| AI 결과는 **코드가 다시 검증**하고, 통과한 것만 지도에 올린다 | AI 출력을 그대로 믿지 않는다 |
| 토큰 · 키는 환경변수로만 | 커밋 금지 (`CLAUDE.md` §4) |
| 실제 게시물 캡션을 저장소에 커밋하지 않음 | 위 저작권 원칙. 테스트 샘플은 직접 만든 가상 캡션 |

## 2. 파이프라인 (5단계)

| 단계 | 하는 일 | 입력 → 출력 | 실패하면 |
|---|---|---|---|
| ① 수집 | 공식 API(Business Discovery = 다른 계정의 공개 게시물 조회 기능)로 대상 계정의 최근 게시물 조회 | 계정명 → 게시물(`id`, `caption`, `permalink`, `timestamp`) | 그 계정만 건너뛰고 로그, 다음 계정 진행 |
| ② 정리 | AI가 캡션을 칸에 맞게 정리 | `caption` → `{행사 여부, 제목, 카테고리, 시작일, 종료일, 시간 원문, 장소명}` | 형식이 틀리면 `FAILED`로 기록, 지도 제외 |
| ③ 좌표 | 카카오 장소(키워드) 검색으로 장소명 → 좌표 | 장소명 → 위도·경도 | 못 찾으면 `NO_COORD`(보류), 지도 제외 |
| ④ 저장 | 게시물 `id` 기준으로 중복 없이 저장 · 갱신 | | 같은 `id`는 갱신 (재실행해도 중복 X) |
| ⑤ 표시 | 마커 + 상세 패널에 인스타 원문 링크 (임베드는 보조) | | 링크 버튼만 숨김 |

| 항목 | 상태 | 내용 |
|---|---|---|
| 조회 대상 | ✅ 확인됨 | 다른 **프로페셔널(비즈니스·크리에이터) 계정**만. 개인 계정은 조회 불가 |
| 요청하는 쪽 | ✅ 확인됨 | 내 계정도 프로페셔널 계정 ID + 앱 사용자 토큰이 필요 |

| 내 인스타 계정 ID 얻는 법 | ✅ 확인됨 (0단계) | 토큰 점검 결과(`granular_scopes` = 토큰에 허용된 페이지·계정 목록)에 인스타 계정 ID가 들어 있음. 반면 `me/accounts`(내가 관리하는 페이지 목록 조회)는 페이지를 0개로 돌려줘서 목록 조회로는 못 찾았고 **원인은 미확인**. 수집 클라이언트는 ID를 설정값(환경변수)으로 받는 쪽이 안전 |
| 로그인 방식 선택 | ⚠️ 미확인 | 앱 대시보드에서 Facebook Login 방식은 '구형(legacy)'으로 표시되고 새 기능은 통합 로그인 방식에만 추가된다고 안내됨. 0단계는 Facebook Login 방식으로 성공. 통합 로그인 방식에서도 `caption`이 오는지는 미시험 |

## 4. 데이터 모델 (결정 필요)

현재 `Event`는 `idx`(재단 원본 PK), `title`, `category`, 좌표, `pubDate`가 **NOT NULL**이고 `idx`는 unique이다 (`Event.java:27-60`). 그리고 찜(`Favorite`)은 `Event`의 PK(`event_id`)를 직접 가리킨다 (`Favorite.java:44`). 인스타 행사에는 재단 `idx`가 없다.

| 안 | 내용 | 장점 | 단점 |
|---|---|---|---|
| A | 별도 테이블 `instagram_event`, `/api/events` 응답에서 합쳐 내려줌 | `Event`를 안 건드림 | **찜이 안 붙음** (`Favorite`이 `Event`만 가리킴) |
| B | `Event`에 `source` · `sourceKey` 추가, `idx`를 nullable로 변경 | 한 곳에 모임, 찜 그대로 동작 | 이미 있는 NOT NULL을 푸는 변경이 `ddl-auto=update`(JPA가 테이블을 자동 변경하는 설정, 운영도 이 값 `application-prod.properties:16`)로는 안 될 가능성이 큼 → **Flyway**(DB 구조 변경을 파일로 관리하는 도구) 먼저 (`PROGRESS.md` "나중에 할 일"과 연결) |
| C | `Event`에 `source` · `sourceKey` 추가, 인스타 행사의 `idx`는 임시 음수값 | 스키마 변경 최소 | 의미 없는 값이 unique 칸에 들어가 지저분함 (비추천) |

- 어느 안이든 **원본 게시물 처리 상태**는 별도 테이블 `instagram_post`에 둔다. 게시물 `id`를 unique로 해서 재실행해도 중복되지 않게 한다.
- 처리 상태값: `PENDING`(수집됨) / `PARSED`(정리됨) / `NO_COORD`(좌표 못 찾아 보류) / `NEEDS_REVIEW`(사람 확인 대기, 8번 5번을 택할 때만) / `READY`(지도 노출) / `FAILED` / `SKIPPED`(행사 아님)
- `Event`로 승격할 때 NOT NULL 칸 채우는 규칙: `category`는 AI 출력값, 비면 `"기타"`(재단 `"전체"` → `"기타"` 처리와 같은 방식, `EventSyncService.java:65`) / `pubDate`는 게시물 `timestamp`를 한국 시간으로 변환
- 권장: **B** (찜이 그대로 동작하는 게 사용자에게 가장 자연스러움). 단 Flyway 도입이 먼저라 PR이 하나 늘어난다.
- `ddl-auto=update`가 기존 컬럼의 NOT NULL을 풀지 않는다는 점은 일반적으로 알려진 동작이며, 착수 때 실제로 확인한다.
- 현재 동기화는 삭제 로직이 없어서 (`EventSyncService.java:78-103`) B안에서도 기존 재단 동기화가 인스타 행사를 지우지는 않는다.

## 5. AI 정리 단계의 약속

**입력:** `caption`(글)
**출력(JSON):** `isEvent` · `title` · `category` · `startDate` · `endDate` · `timeText` · `placeName` — 모르는 칸은 `null`
**`timestamp`의 용도:** `pubDate`를 채우고 정렬에 쓰는 것뿐이다. **연도를 추정하는 데는 쓰지 않는다** (UTC로 오므로 저장 때 한국 시간으로 변환).

코드가 AI 출력을 받은 뒤 **다시 검사**한다 (AI 말을 그대로 믿지 않음).

| 검사 | 이유 |
|---|---|
| JSON 형식 · 허용된 칸만 | 엉뚱한 출력 방지 |
| 날짜 형식, 시작일 ≤ 종료일 | 잘못된 기간 방지 |
| 날짜 숫자가 **캡션 원문에도 있는지** 대조 | AI가 없는 날짜를 지어내는 것(환각) 방지 |
| 제목 · 장소 · 시간 길이 제한 | DB 칸 길이를 넘으면 저장이 실패할 수 있음 (PR #23 리뷰에서 지적되어 머지 전에 고친 위험) |
| `isEvent=false`(후기 · 광고 · 공지)는 `SKIPPED` | 행사가 아닌 글 제외 |

- 연도가 글에 없으면 **추측하지 않고 `null`**. 날짜가 `null`이면 지도에 올리지 않는다.
- AI 호출은 인터페이스 뒤에 두고, 테스트에서는 **가짜 구현**을 쓴다.
- AI 공급자(Gemini 무료 한도 / Ollama 내 PC)는 **미결정** (8번). 클라우드 세션에서는 둘 다 쓸 수 없다고 가정하고, 실제 호출은 사용자 PC에서 확인한다.

## 6. 작업 순서 (한 PR = 한 목적)

| 순서 | 작업 | 키 필요 | 검증 |
|---|---|---|---|
| **0** | ✅ **Meta 사전 확인 (코드 없음) — 완료 2026-10-31.** 사용자 PC에서 Business Discovery 실호출(대상 1계정, 본인 앱 토큰) → `caption` 등 5개 필드 수신 확인. 권한 · 검수 · 약관은 3번 표에 남은 항목으로 정리 | ✔ Meta | 사용자 PC |
| 1 | 캡션 정리기 — 인터페이스 · 출력 검증 · 직접 만든 가상 캡션으로 단위 테스트 | ✗ | CI |
| 2 | 장소 → 좌표 (카카오 로컬 검색, 수원 범위 검사). 지금 저장소에는 장소 검색 호출이 없고 REST 키는 로그인에만 쓰임 | 운영에서 ✔ 카카오 REST 키 (테스트는 가짜 응답이라 ✗) | CI |
| 3 | 데이터 모델 (4번 결정 후, B안이면 Flyway 먼저) | ✗ | CI + 사용자 PC |
| 4 | 수집 클라이언트 (Business Discovery) | ✔ Meta 토큰 | 사용자 PC |
| 5 | 저장 · 동기화 연결 (처리 상태 흐름) | ✔ | 사용자 PC |
| 6 | 지도 표시 (원문 링크, 임베드는 선택) | ✗ | 사용자 기기 |

0단계를 맨 앞에 두는 이유: 1~3번이 "`caption`이 온다"는 가정 위에 지어지는데, 그 가정이 4번에서야 확인되면 앞 작업을 다시 해야 할 수 있다.

0단계에서 못 끝낸 확인의 시점:
- **약관 확인은 3번(데이터 모델) 전에** 끝낸다. 저장하는 값의 범위가 약관에 따라 달라질 수 있기 때문이다.
- 장기 토큰 교환 · Live 모드 검수 여부 · 호출 제한은 4번(수집 클라이언트)에서 확인한다.

## 7. 오류 위험 위치

| # | 위치 | 무엇이 잘못될 수 있나 | 대비 |
|---|---|---|---|
| 1 | 캡션 형식 | 이모지 라벨(📅 📍)로 쓰는 글, 줄글, 해시태그 위주 등 제각각 | 가상 캡션 샘플로 테스트 · 모르면 `null` |

| 3 | 연도 생략 | "11.7~11.18"의 연도 | 추측하지 않고 `null` |
| 4 | **장소 별칭 · 지역명** 🔥 | "행궁동 일대" 같은 말이 엉뚱한 곳으로 검색됨 → 지도에 **틀린 위치** | 검색 결과가 수원 범위 안인지 검사, 1건으로 좁혀지지 않으면 `NO_COORD` |
| 5 | AI 환각 | 없는 날짜 · 장소를 만듦 | 5번의 원문 대조 |
| 6 | 중복 | 재단 API 행사와 같은 행사, 재게시 | 제목 + 날짜 + 장소로 후보 표시, 재단 데이터 우선 |
| 7 | 삭제 · 비공개 게시물 | 링크가 깨지는데 `id` 재조회로는 못 알아냄 (3번 제약 ②) | 다음 수집 때 목록에서 사라졌는지로 판단하는 방식을 4번(수집 클라이언트) 단계에서 검토. 그 전엔 링크 버튼이 깨질 수 있음을 감수 |
| 8 | 토큰 만료 | 장기 토큰도 60일 뒤 만료 → 수집이 조용히 실패 | 원인을 로그에 남기고, 갱신 시점 관리 |
| 9 | 호출 제한 | 계정 수 · 실행 주기가 크면 차단 | 계정 수 · 주기를 작게 시작 (제한 수치는 미확인) |
| 10 | AI 비용 · 한도 | 무료 한도 초과 | 새 게시물만 처리, 처리한 `id`는 건너뜀 |
| 11 | 비밀값 | 토큰이 코드나 로그에 남음 | 환경변수만, 로그에 키 이름만 |
| 12 | 약관 | 허용 범위를 벗어난 저장 · 가공 | 3번(데이터 모델) 전에 약관 문서를 직접 읽어 확인, 불확실하면 저장하는 값을 줄임(추출값 + `permalink`만) |

## 8. 열린 결정 (착수 전에 사용자가 정한다)

1. **데이터 모델** A / B / C (4번)
2. **AI 공급자** Gemini(무료 한도) / Ollama(내 PC)
3. **대상 계정 목록** — 0단계에서 `suwon_city` 조회가 성공함. 다른 후보 계정은 아직 정하지 않았고, 프로페셔널 계정 여부도 **미확인**
4. **캡션 원문 저장 여부** — 저장하면 재처리가 쉽지만 저작권 · 약관 · 개인정보 부담. 권장: 추출값 + `permalink`만 저장
5. **사람 확인 단계** — 통과한 것을 바로 지도에 올릴지(`READY`), 한 번 확인 후 올릴지(`NEEDS_REVIEW`)

## 9. 사용자가 미리 준비할 것 (Meta)

1. 인스타 계정을 **프로페셔널 계정**(비즈니스 또는 크리에이터)으로 전환
2. **페이스북 페이지**를 만들고 인스타 계정과 연결 (Facebook Login 방식에서 필요)
3. Meta 개발자 등록 + 앱 만들기. 0단계에서 실제로 한 방법: 앱 만들기 → 이용 사례 "Instagram에서 메시지 및 콘텐츠 관리" 선택 → 설정 화면에서 "Facebook 로그인이 포함된 API" 선택 → "권한 및 기능"에서 권한 4개 추가 (이 4개가 모두 필요한지는 3번 표 참조)
4. 토큰은 Graph API 탐색기에서 발급 (0단계에서 사용). 로그인 팝업에서 페이지 1개 · 인스타 계정 1개만 허용하고(허용 범위를 줄이는 쪽 권장), 토큰은 **환경변수로만** 보관 (`.env` · 운영 환경변수, 커밋 금지)
