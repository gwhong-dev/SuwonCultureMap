# 인스타그램 게시글 연동 — 설계 (초안)

> **상태: 설계만 (코드 없음).** 구현은 아래 "6. PR 쪼개기" 순서로 따로 진행한다.
> **확인됨** = Meta 공식 문서에서 읽은 것, **미확인** = 문서에서 찾지 못한 것. 미확인 항목은 구현 착수 때 다시 확인한다.

## 1. 목적과 원칙

수원문화재단 API에 없는 행사(인스타에만 올라오는 지역 행사)를 같은 지도에 추가한다.

| 원칙 | 이유 |
|---|---|
| 크롤링(자동 긁기) 안 함, 공식 API만 | 약관 위반 위험 · 계정 차단 · 포트폴리오에 부적합 |
| 사진은 복사하지 않고 원본 링크(`permalink`)만 보관 | 저작권 |
| AI가 못 읽으면 **비워 둔다**(null) | 틀린 값을 넣는 것보다 낫다 (캘린더 B안과 같은 원칙, PR #23) |
| AI 결과는 **코드가 다시 검증**하고, 통과한 것만 지도에 올린다 | AI 출력을 그대로 믿지 않는다 |
| 토큰 · 키는 환경변수로만 | 커밋 금지 (`CLAUDE.md` §4) |

## 2. 파이프라인 (5단계)

| 단계 | 하는 일 | 입력 → 출력 | 실패하면 |
|---|---|---|---|
| ① 수집 | 공식 API(Business Discovery)로 대상 계정의 최근 게시물 조회 | 계정명 → 게시물(`id`, `caption`, `permalink`, `timestamp`) | 그 계정만 건너뛰고 로그, 다음 계정 진행 |
| ② 정리 | AI가 캡션을 칸에 맞게 정리 | `caption` → `{행사 여부, 제목, 시작일, 종료일, 시간 원문, 장소명}` | 형식이 틀리면 `FAILED`로 기록, 지도 제외 |
| ③ 좌표 | 카카오 장소(키워드) 검색으로 장소명 → 좌표 | 장소명 → 위도·경도 | 못 찾으면 보류 상태, 지도 제외 |
| ④ 저장 | 게시물 `id` 기준으로 중복 없이 저장 · 갱신 | | 같은 `id`는 갱신 (재실행해도 중복 X) |
| ⑤ 표시 | 마커 + 상세 패널에 인스타 원문 링크 (임베드는 보조) | | 링크 깨짐(삭제·비공개)은 버튼만 숨김 |

## 3. Meta 공식 문서 확인 결과

| 항목 | 상태 | 내용 |
|---|---|---|
| 조회 대상 | ✅ 확인됨 | 다른 **프로페셔널(비즈니스·크리에이터) 계정**만. 개인 계정은 조회 불가 |
| 요청하는 쪽 | ✅ 확인됨 | 내 계정도 프로페셔널 계정 ID + 앱 사용자 토큰이 필요 |
| 로그인 방식 | ✅ 확인됨 | Facebook Login 방식 / Unified Login 방식 두 가지를 지원 |
| 게시물 필드 | ✅ 확인됨 | `caption` · `permalink` · `timestamp` · `media_type` · `id`는 공개 필드. 단 `caption`은 **Facebook Login 방식에서만** 쓸 수 있다고 적혀 있음 |
| Business Discovery에서 위 필드가 쓰이는지 | ⚠️ 미확인 | Business Discovery 문서에는 필드가 직접 나열되지 않음. 공개 필드는 필드 확장으로 읽는다는 설명만 있음 → 착수 때 실제 호출로 확인 |
| 필요한 권한 이름 | ⚠️ 미확인 | 읽은 문서들에 없음 (엔드포인트 레퍼런스 참조라고만 되어 있음) |
| 앱 검수(App Review) | ⚠️ 미확인 | "내가 소유·관리하는 비즈니스용 앱"은 검수 불필요라는 표가 있으나, **남의 공개 계정을 읽는 우리 경우에 해당하는지** 문서로 확인 안 됨 |
| 개발 모드 / 역할 사용자만 쓸 때 | ⚠️ 미확인 | 문서에 언급 없음 |
| 페이스북 페이지 연결 필요 여부 | ⚠️ 미확인 | Business Discovery 문서에 없음. Facebook Login 방식이면 필요할 가능성이 있음 (추정) |
| 호출 제한 | ⚠️ 미확인 | 공식 문서에 없음. 이전에 본 "시간당 200 × 앱 사용자 수"는 **비공식 블로그** 수치 |
| 토큰 만료 · 갱신 | ⚠️ 미확인 | 착수 때 확인 |

## 4. 데이터 모델 (결정 필요)

현재 `Event`는 `idx`(재단 원본 PK)가 **NOT NULL + unique**, 좌표도 NOT NULL이다 (`Event.java`). 그리고 찜(`Favorite`)은 `Event`의 PK(`event_id`)를 직접 가리킨다 (`Favorite.java:44`). 인스타 행사에는 재단 `idx`가 없다.

| 안 | 내용 | 장점 | 단점 |
|---|---|---|---|
| A | 별도 테이블 `instagram_event`, `/api/events` 응답에서 합쳐 내려줌 | `Event`를 안 건드림 | **찜이 안 붙음** (`Favorite`이 `Event`만 가리킴) |
| B | `Event`에 `source` · `sourceKey` 추가, `idx`를 nullable로 변경 | 한 곳에 모임, 찜 그대로 동작 | 이미 있는 NOT NULL을 푸는 변경이 `ddl-auto=update`로는 안 될 가능성이 큼 → **마이그레이션 도구(Flyway) 먼저** (PROGRESS "나중에 할 일"과 연결) |
| C | `Event`에 `source` · `sourceKey` 추가, 인스타 행사의 `idx`는 임시 음수값 | 스키마 변경 최소 | 의미 없는 값이 unique 칸에 들어가 지저분함 (비추천) |

- 어느 안이든 **원본 게시물 처리 상태**(`PENDING` / `PARSED` / `GEOCODED` / `FAILED` / `SKIPPED`)는 별도 테이블 `instagram_post`에 둔다. 게시물 `id`를 unique로 해서 재실행해도 중복되지 않게 한다.
- 내 권장: **B** (찜이 그대로 동작하는 게 사용자에게 가장 자연스러움). 단 Flyway 도입을 먼저 해야 해서 PR이 하나 늘어난다.
- `ddl-auto=update`가 기존 컬럼의 NOT NULL을 풀지 않는다는 점은 일반적으로 알려진 동작이며, 착수 때 실제로 확인한다.

## 5. AI 정리 단계의 약속

**입력:** `caption`(글) + `timestamp`(게시 시각)
**출력(JSON):** `isEvent` · `title` · `startDate` · `endDate` · `timeText` · `placeName` — 모르는 칸은 `null`

코드가 AI 출력을 받은 뒤 **다시 검사**한다 (AI 말을 그대로 믿지 않음).

| 검사 | 이유 |
|---|---|
| JSON 형식 · 허용된 칸만 | 엉뚱한 출력 방지 |
| 날짜 형식, 시작일 ≤ 종료일 | 잘못된 기간 방지 |
| 날짜 숫자가 **캡션 원문에도 있는지** 대조 | AI가 없는 날짜를 지어내는 것(환각) 방지 |
| 제목 · 장소 · 시간 길이 제한 | DB 칸 길이 초과로 저장이 멈춘 PR #23의 교훈 |
| `isEvent=false`(후기 · 광고 · 공지)는 `SKIPPED` | 행사가 아닌 글 제외 |

- 연도가 글에 없으면 **추측하지 않고 `null`** (모호하면 비운다).
- AI 호출은 인터페이스 뒤에 두고, 테스트에서는 **가짜 구현**을 쓴다 (클라우드·CI에는 키가 없음).
- AI 공급자(Gemini 무료 한도 / Ollama 내 PC)는 **미결정** (아래 8번).

## 6. PR 쪼개기 (한 PR = 한 목적)

키가 필요 없는 것부터, CI로 검증되는 것부터 간다.

| 순서 | PR | 키 필요 | 검증 |
|---|---|---|---|
| 1 | 캡션 정리기 — 인터페이스 · 출력 검증 · 실제 캡션 샘플로 단위 테스트 | ✗ | CI |
| 2 | 장소 → 좌표 (카카오 로컬 검색, 수원 범위 검사) | ✗ (테스트는 가짜 응답) | CI |
| 3 | 데이터 모델 (4번 결정 후, B안이면 Flyway 먼저) | ✗ | CI + 사용자 PC |
| 4 | 수집 클라이언트 (Business Discovery) | ✔ Meta 토큰 | 사용자 PC |
| 5 | 저장 · 동기화 연결 (처리 상태 흐름) | ✔ | 사용자 PC |
| 6 | 지도 표시 (원문 링크, 임베드는 선택) | ✗ | 사용자 기기 |

## 7. 오류 위험 위치

| # | 위치 | 무엇이 잘못될 수 있나 | 대비 |
|---|---|---|---|
| 1 | 캡션 형식 | 이모지 라벨(📅 📍)로 쓰는 글, 줄글, 해시태그 위주 등 제각각 | 실제 캡션 샘플을 모아 테스트 · 모르면 `null` |
| 2 | 게시물 하나에 행사 여러 개 / 여러 회차 | 첫 번째만 쓰면 틀림 | 처음엔 1게시물 = 1행사만 인정, 나머지는 `SKIPPED` |
| 3 | 연도 생략 | "11.7~11.18"의 연도 | 추측하지 않고 `null` |
| 4 | **장소 별칭 · 지역명** 🔥 | "행궁동 일대" 같은 말이 엉뚱한 곳으로 검색됨 → 지도에 **틀린 위치** | 검색 결과가 수원 범위 안인지 검사, 1건으로 좁혀지지 않으면 보류 |
| 5 | AI 환각 | 없는 날짜 · 장소를 만듦 | 5번의 원문 대조 |
| 6 | 중복 | 재단 API 행사와 같은 행사, 재게시 | 제목 + 날짜 + 장소로 후보 표시, 재단 데이터 우선 |
| 7 | 삭제 · 비공개 게시물 | 링크가 깨짐 | 링크 버튼만 숨김, 행사 정보는 유지 |
| 8 | 토큰 만료 | 수집이 조용히 실패 | 원인을 로그에 남김 (갱신 방식은 착수 때 확인) |
| 9 | 호출 제한 | 계정 수 · 실행 주기가 크면 차단 | 계정 수 · 주기를 작게 시작 (제한 수치는 미확인) |
| 10 | AI 비용 · 한도 | 무료 한도 초과 | 새 게시물만 처리, 처리한 `id`는 건너뜀 |
| 11 | 비밀값 | 토큰이 코드나 로그에 남음 | 환경변수만, 로그에 키 이름만 |

## 8. 열린 결정 (착수 전에 사용자가 정한다)

1. **데이터 모델** A / B / C (4번)
2. **AI 공급자** Gemini(무료 한도) / Ollama(내 PC) — 클라우드 세션에서는 둘 다 실행 불가라 사용자 PC에서 확인
3. **대상 계정 목록** — 이전 검토 때 공식 계정 후보 2곳이 나왔으나, 실제 계정명과 프로페셔널 계정 여부는 **미확인**
4. **캡션 원문 저장 여부** — 저장하면 재처리가 쉽지만 저작권 · 개인정보 부담. 권장: 추출값 + `permalink`만 저장
5. **사람 확인 단계** — 통과한 것을 바로 지도에 올릴지, 한 번 확인 후 올릴지

## 9. 사용자가 미리 준비할 것 (Meta)

1. 인스타 계정을 **프로페셔널 계정**(비즈니스 또는 크리에이터)으로 전환
2. Meta 개발자 계정 + **앱 만들기**
3. Facebook Login 방식 설정 (캡션이 이쪽에서만 문서에 명시됨). 페이스북 페이지 연결이 필요한지는 착수 때 확인
4. 앱 사용자 토큰 발급 → **환경변수로만** 보관 (`.env` · 운영 환경변수, 커밋 금지)

단계별 화면 안내는 채팅으로 따로 한다.
