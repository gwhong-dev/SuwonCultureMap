## 2. 요청 · 응답 (realm2 실사용 예 기준)

**요청 파라미터**

| 이름 | 예 | 비고 |
|---|---|---|
| `serviceKey` | (키) | 키 값은 커밋 · 채팅 금지 |
| `PageNo` · `numOfrows` | 1 · 100 | **대소문자 섞임** — 틀리면 조용히 기본값으로 돌아감 |
| `from` · `to` | `20261101` · `20261231` | 기간과 겹치는 행사 |
| `sido` | `경기` | 시 · 도 이름 |
| `realmCode` | `D000`(전시) | 분야 코드 |
| `serviceTp` | `A` | |
| `gpsxfrom` · `gpsyfrom` · `gpsxto` · `gpsyto` | | 옛 문화포털 API(`publicperformancedisplays/period`)에 있던 좌표 범위 검색. **cultureinfo 에서도 되는지 미확인** → 안 되면 `sido=경기` 로 받고 `sigungu` · 좌표로 우리가 거름 |

**응답 항목 (목록)**: `seq`(행사 번호) · `title` · `startDate` · `endDate` · `place` · `realmName`(분야) · `area`(시도) · `sigungu`(시군구) · `gpsX`(**경도**) · `gpsY`(**위도**) · `thumbnail` · `totalCount`
- 요금은 목록에 없음 → `detail2` 로 따로 받아야 함 (V7 `fee` 칸 채우려면 행사마다 1회 추가 호출)
- 오류는 HTTP 200 + `OpenAPI_ServiceResponse` 루트 (`SERVICE_KEY_IS_NOT_REGISTERED_ERROR` · `LIMITED_NUMBER_OF_SERVICE_REQUESTS_EXCEEDS_ERROR` · `SERVICE_ACCESS_DENIED_ERROR`) → 정상 응답과 루트 태그로 구분해야 함

## 3. 수원 행사 수 추정

- **실측 없음.** 수원 범위 = 위도 37.21~37.34, 경도 126.93~127.09 (시 경계를 덮는 사각형, 오산 · 화성 · 용인 일부가 섞일 수 있어 `sigungu` 가 "수원" 인지로 한 번 더 거름)
- 짐작: 국가 · 도 단위 시설(경기아트센터 · 수원시립미술관 · 수원SK아트리움 · 국립농업박물관 등) 공연 · 전시 위주. 재단 API(지금 운영 약 150건)는 재단 행사 중심이라 **둘이 겹치지 않는 시설 행사가 늘어날 가능성**은 있음 — 숫자는 5번 실측으로 확인

## 4. 재단과 겹치는 방식 · 넣을 때 필요한 작업

**겹치는 방식** — 이미 있는 "같은 행사 합치기"(`docs/event-merge.md`, `service/merge/`)를 그대로 씀
- 날짜 겹침 + 좌표 300m 또는 장소명 같음 + 제목 유사 → 한 묶음, **재단 우선 대표** (규칙 3번)
- 새 출처 우선순위: 재단(`SWCF`) → **한눈에(`CULTUREINFO`, 새로)** → 인스타 개별 → 인스타 모음. 정형 데이터라 인스타보다 위
- 주의: 재단 XML 은 lat/lng 가 뒤바뀌어 옴(`EventSyncService` 124줄) — 새 출처는 `gpsY`=위도 · `gpsX`=경도로 바르게 넣고, 합치기 거리 계산이 두 출처에서 같은 축인지 시험으로 고정

**넣을 때 작업 (예상 등급 L)**

| # | 작업 | 메모 |
|---|---|---|
| 1 | `Event.SOURCE_CULTUREINFO` + `(source, source_key=seq)` 로 중복 방지 | 스키마는 V2 의 `source` · `source_key` 재사용 → migration 없을 수도 |
| 2 | 수집기: `area2`(경기) 또는 `period2` 페이지 돌기 → 수원만 거름 → 저장 | 06 · 18시 동기화(`ScheduledSyncJob`)에 붙이고 운영 스위치(환경변수)로 켜고 끔. 인스타처럼 |
| 3 | 분류(`realmName`) → 우리 분류(공연 · 전시 · 행사 …) 매핑 | |
| 4 | 구(`district`): 좌표 → 행정구역(D1 과 같은 방식) | |
| 5 | 요금 · 문의는 `detail2` (행사당 1회) — 하루 한도 안 | 처음엔 비워 둬도 화면은 원문 링크로 대체 |
| 6 | 화면 · 처리방침: 출처 표시 "한국문화정보원" + 라이선스 표기(공공누리 유형 확인 뒤) | |
| 7 | 시험: 가짜 XML 로 파싱 · 수원 거르기 · 재단과 합치기 · 오류 응답 | |

## 5. 결정을 위한 실측 (서비스키 필요 — 사용자 PC)

**① 키 발급 · 활용신청**
1. https://www.data.go.kr/data/15138937/openapi.do 열기 → 로그인
2. "활용신청" → 목적 "개인 포트폴리오 웹서비스" → 신청 (보통 자동 승인)
   - 되어 있나요? → 마이페이지 › 데이터 활용 › Open API › 활용신청 현황에 "승인" 이면 성공
3. 같은 페이지에서 **갱신 주기 · 이용허락범위(공공누리 유형) · 트래픽** 칸을 확인해 이 문서 1번에 적기
4. 승인 직후엔 `SERVICE_KEY_IS_NOT_REGISTERED_ERROR` 가 1~2시간 날 수 있음 → 기다렸다 다시

**② 키 넣기** (값은 채팅 · 커밋 금지)
- 로컬: `application-dev.properties` 에 키 이름만 정해 추가 (예: `cultureinfo.api-key=`), 파일은 gitignore 라 커밋 안 됨
- 운영은 실측 단계에선 넣지 않음 (넣기로 결정한 뒤 `.env` 환경변수)

**③ 잴 것** (Claude 가 로컬에서 호출 · 결과만 기록)
- `area2` `sido=경기`, 이번 달~+2달 → 전체 수 · `sigungu` 에 "수원" 들어간 수 · 좌표 사각형 안 수
- 좌표 범위 파라미터(`gpsxfrom` …)가 cultureinfo 에서 먹는지 (넣었을 때 `totalCount` 가 줄어드는지)
- 운영 `/api/events` 와 비교: 합치기 기준(날짜 · 300m · 제목)으로 **겹치는 수 / 새로 늘어나는 수**
