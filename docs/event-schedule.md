# 실제 진행 날짜 정제 — 설계

> 코드보다 먼저 **읽는 곳 · 규칙 · 데이터 모델 · 테스트**를 정한다. 구현 순서는 11번, 결정은 12번.
> 관련: `docs/event-merge.md` 3번, `docs/instagram-integration.md` 3-1 · 5번 · 8번, PROGRESS.md "실제 진행 날짜 정제"

## 1. 문제와 원칙

행사는 시작일~종료일만 저장한다. 그래서 며칠만 하는 행사도 `5/16 ~ 9/19` 로 보여 **중간 날짜에 갔다가 허탕 칠 수 있다.** 인스타는 `매주 금~일` 이 `NO_DATE`, 여러 회차가 `PENDING` 으로 빠져 지도에 아예 안 나온다.

1. **기간(시작~종료)은 그대로 둔다.** 진행 날짜는 따로 저장한다. 합치기 · 지난 행사 판별은 지금처럼 기간을 쓴다
2. **틀린 날짜를 안내하는 것보다 원문을 보여 주는 것이 낫다.** 못 읽으면 추측하지 않고 원문을 표시한다
3. **"못 읽음"과 "매일 진행"은 다르다.** 기간만 있고 요일이 안 적혀 있으면 매일이라고 단정하지 않는다
4. **원본을 고치지 않고 매번 다시 계산한다** (멱등 — 몇 번 돌려도 같은 결과). 합치기와 같은 방식
5. 재단 먼저, 인스타는 나중

### 2-3. 7일 이상 58건의 실제 일정 (시간 칸 · 요일 칸 · 본문을 사람이 읽어 분류)

XML 의 `description`(행사 소개 본문, HTML)은 지금 받지 않는다(`EventItem.java` 주석: 태그가 섞여 파싱이 꼬임). 이번에 본문까지 읽어 보니 **실제 일정은 대부분 본문에 있었다.** 분류는 사람 판단이므로 구현 때 다시 확인한다. id 목록은 부록.

| 실제 일정 | 전체 58 | 좌표 49 | 진행 중 · 예정 | 예 |
|---|---:|---:|---:|---|
| ① 며칠만 하는 회차 나열 | 20 | 16 | 4 | `2026. 10. 31.(토), 11. 1.(일), 11. 7.(토), …` |
| ② 매주 요일 | 8 | 7 | 3 | `기간 중 매주 금~일요일, 공휴일`, `5·6·9·10월 매주 금·토·일` |
| ③ 매주 문구와 회차 표가 어긋남 | 2 | 2 | 0 | `매주 금, 토요일` 이라 적혔는데 10월 표에는 토요일만 |
| ④ 쉬는 요일 있음 | 12 | 10 | 1 | `(화요일 ~ 일요일) ※ 월요일 및 법정공휴일은 …` |
| ⑤ 요일 제한 표기 없음 | 8 | 8 | 2 | `기간 : 2025. 7. 3.(금) ~ 8. 24.(일), 10:00~18:00` |
| ⑥ 판단 불가 (프로그램별로 다름 · 본문 비어 있음 · 공모전 등) | 8 | 6 | 1 | 축제 전체 프로그램, 이미지만 있는 글 |

**"진행 중 · 예정"은 종료일이 2026-11-01 이후인 행**이다. 129건 중 22건, 7일 이상은 11건이고 나머지는 이미 끝난 행이다.

**이 표에서 나온 결론**

1. **"7일 이상 50건 중 약 10건" 추정은 작았다.** 키워드 추정이 맞던 것은 `시간` 칸의 글자뿐이다. 실제로 기간 내내 진행하지 않는 행사는 58건 중 **42건(①~④)**, 좌표 있는 행 기준 49건 중 35건이다
2. **`시간` 칸만 읽으면 거의 못 잡는다.** ①~③ 30건 중 `시간` · `요일` · `추가회차` 칸만으로 바르게 읽히는 것은 **2건**(idx 2955 특정 날짜 · 2970 요일 칸)이다. 일부만 읽히는 것 3건(2972 · 2953 · 2958), 달별 시간표 1건(3011)을 뺀 24건은 단서가 없다
3. **`시간` 칸이 시간뿐인 7일+ 27건 중 13건은 며칠 · 매주 행사이고, 4건은 쉬는 요일이 있다.** 예: idx 3035 `19:30` 은 9/11 · 10/23 **이틀뿐**, idx 3051 `13:00~19:00` 은 23일 중 6일
4. **`토요일 14:00` 을 "매주 토요일"로 읽으면 틀린다.** 지금까지 대표 예시로 쓴 idx 2972(`5/16 ~ 9/19`)는 본문에 `2026. 5. 16.(토) / 9. 19.(토) 총 2회` 라고 적혀 있다. 매주로 펼치면 **토요일 19일을 안내하고 17일이 허탕**이다 → 카드 표시 예시도 `토요일만` 이 아니라 `총 2회 · 5/16, 9/19` 가 맞다

## 3. 추출 규칙

순수 계산 클래스 `ScheduleExtractor`(가칭, DB · 네트워크 없음)가 칸 값과 본문을 받아 **날짜 목록 또는 "모름"** 을 돌려준다. `service/caption/` 과 같은 구조다.

### 읽는 순서 (앞에서 확정되면 멈춤)

| 순서 | 경우 | 읽는 곳 | 결과 |
|---|---|---|---|
| 1 | 시작일 = 종료일 | XML `eventDate` | 그 하루. 52건은 규칙 없이 확정 |
| 2 | 날짜 나열 (`~` 로 이어지지 않은 2개 이상) | `시간` 칸 → 본문 **허용 라벨 줄** | 적힌 날짜 |
| 3 | `매주` + 요일 (`기간 중 매주 금~일요일`, `매주 토/일요일`) | `요일` 칸 → 본문 허용 라벨 줄 | 기간 안의 그 요일 전부 |
| 4 | 요일 범위 · 쉬는 요일 (`화요일 ~ 일요일`, `월 휴관`) | `시간` · `요일` 칸 → 본문 허용 라벨 줄 | 기간 안에서 그 요일만 / 그 요일 빼고 |
| 5 | `매일` 이 적힘 | 본문 허용 라벨 줄 | 기간 전체 |
| 6 | 그 밖 전부 | — | **모름** → 기간 + 원문 표시 |

- **허용 라벨**: `운영일` · `운영일자` · `운영일정` · `운영일시` · `행사일정` · `행사일시` · `공연일시` · `진행일시` · `일시` · `일정` · `기간` · `관람기간` · `전시기간` · `해설기간` · `체험요일` · `관람시간`(요일 범위를 읽기 위해 구현 때 추가)
- **금지 라벨** (이 줄의 날짜는 절대 쓰지 않음): `접수` · `신청` · `예매` · `예약` · `티켓` · `모집` · `환불` 이 들어간 줄. 칸 값에도 똑같이 적용
- **요일 고정(`토요일 14:00`)만으로는 펼치지 않는다.** "매주" 근거가 없다. 본문에 날짜가 있으면 2번에서 확정되고, 없으면 모름

### 본문 가져오기

- Jackson 매핑으로 받지 않는다 (`EventItem.java` 의 이유 그대로). **원문 XML 에서 `<item>` 별로 `<description>` 만 잘라** idx 로 연결한다. 이 방식으로 129건 모두 문제없이 잘렸음을 조사 스크립트로 확인. HTML 표기가 이중 인코딩이라(`&amp;nbsp;`) 풀기를 2번 해야 하고, 표 칸은 `|` 로 이어 붙인다
- **본문은 저장하지 않는다.** 재단 XML 은 동기화 때마다 전체(약 1MB)를 다시 받으므로 재처리에 저장이 필요 없다. 화면에 보일 원문 한 줄(`schedule_text`)만 저장

### AI 는 어디에 쓰나

- 기존 구조와 같다: **규칙 먼저 → 못 읽은 것만 AI → 코드가 다시 검사** (`CaptionParser.parseBlock`, `ParsedEventValidator`)
- **1차 범위에는 AI 를 넣지 않는다.** `CaptionAiClient` 는 아직 구현체가 없어(`AI 미연결` → `PENDING`) AI 연결이 선행되어야 한다
- 나중에 붙일 때: 표 9건 + 모름 중 7일 이상만 보낸다. AI 는 날짜를 만들지 않고 "날짜 목록" 또는 "요일 규칙"만 답한다. 요일 규칙을 날짜로 펼치는 것은 코드가 한다. 4번 검사를 똑같이 통과해야 한다

## 4. 검증 — 맞지 않으면 버린다

코드가 규칙 · AI 결과를 똑같이 검사한다. **날짜 1개라도 실패하면 그 행사의 결과 전체를 버리고 모름으로 둔다** (일부만 맞는 목록은 빠진 날을 "안 함"으로 안내하게 된다).

| 검사 | 실패 예 | 근거 |
|---|---|---|
| 요일이 달력과 맞음 | `2025. 7. 3.(금)` | `CaptionDateParser.weekdayMatches` 와 같은 방식. 2-4 의 368개 중 2개만 실패 |
| 날짜가 기간 안 (시작일 ≤ 날짜 ≤ 종료일) | 신청일이 잘못 섞임 | 2-4 의 41개 |
| 원문에 그 날짜가 있음 (AI 만) | 지어낸 날짜 | `ParsedEventValidator.monthDayInText` 재사용 |
| `총 N회` 가 적혀 있으면 개수가 같음 | idx 2958 `총 8회` ↔ 달력 9일 | 일치 예: 2972 총 2회 · 2932 총 16회 · 3032 총 11회 (직접 셈) |
| 펼친 날짜가 1개 이상 | 기간 안에 그 요일이 없음 | |

**알고 있는 한계**
- XML 기간과 본문 기간이 다른 경우가 있다 (idx 3044: XML `~9/30`, 본문 `~9. 27.` / 2995: XML `8/8~`, 본문 `8. 1.~`). 기간을 건드리지 않는 원칙(1번)대로 XML 을 믿는다. 3044 는 9/28~30 이 틀리게 나올 수 있다
- 본문이 갱신되며 지난 회차가 사라진 행이 있다 (idx 2961 은 5월 시작인데 9월부터의 회차만 있음). 지난 날짜가 빠지는 것은 손해가 없다. 앞으로의 회차가 아직 안 올라온 경우 "나열된 날만 한다"로 잘못 안내할 수 있어 카드에 원문을 같이 보여 준다

## 5. 데이터 모델

| 안 | 방식 | 장점 | 단점 |
|---|---|---|---|
| **① 날짜 표 + 상태 칸 (결정)** | `event_date(event_id, run_date)` 한 날짜당 한 줄 + `event` 에 상태 · 원문 칸 | 며칠 나열 · 매주 · 쉬는 요일을 **모두 같은 모양**으로 저장. "오늘 진행"이 쿼리 한 줄. 합집합 쉬움 | 표가 하나 늘고 행 수 증가 (아래 계산) |
| ② 요일 칸 | `event.weekdays = 'FRI,SAT,SUN'` | 칸 1개, 행 수 없음 | **① 회차 나열 20건을 표현 못 함.** 달 한정 · 예외도 불가 |
| ③ JSON 칸 | `event.dates = '["2026-05-16", …]'` | 표가 안 늘고, 지금은 필터가 브라우저라 충분 | MySQL · H2 함수 차이로 쿼리 · 테스트가 번거로움. 날짜 조회 API 를 만들면 다시 표로 옮겨야 함 |
| ④ 규칙 저장 | RRULE(반복 규칙) + 예외 날짜 | 행이 적고 캘린더 표준에 가까움 | 조회 때마다 펼쳐야 하고 지금 규모에 과함 |

**행 수**: 129건을 전부 매일로 펼쳐도 4,197행 (저장되는 118건은 3,816행, 최장 232일). 실제는 이보다 적다. 부담 없음.

```sql
-- 안 ①. Flyway 버전 번호는 구현 시점에 정한다 (다른 작업과 겹치지 않게)
CREATE TABLE event_date (
  event_id BIGINT NOT NULL,
  run_date DATE NOT NULL,
  PRIMARY KEY (event_id, run_date),
  CONSTRAINT fk_event_date_event FOREIGN KEY (event_id) REFERENCES event (id) ON DELETE CASCADE
);
CREATE INDEX idx_event_date_run_date ON event_date (run_date);
ALTER TABLE event ADD COLUMN schedule_status VARCHAR(20) NOT NULL DEFAULT 'UNKNOWN';
ALTER TABLE event ADD COLUMN schedule_text VARCHAR(1000) NULL;
ALTER TABLE event ADD COLUMN schedule_holiday_note BOOLEAN NOT NULL DEFAULT FALSE; -- 구현 때 추가 (PR #68 검증): 6번 표시에 필요한데 본문을 저장하지 않음
```

- **상태 칸이 필요한 이유**: 날짜 표에 행이 없을 때 "아직 안 읽음 · 못 읽음"을 "안 함"으로 오해하지 않기 위해서다. 값: `DATES`(날짜 표가 정답) / `UNKNOWN`(기간만 믿을 수 있음, 원문 표시)
- 칸 이름은 `date` 대신 `run_date` (MySQL · H2 예약어와 겹치지 않게)
- `ON DELETE CASCADE` 로 행사가 지워지면 날짜도 같이 지워진다 → `scripts/reset-instagram-dev.ps1` 수정 불필요
- **언제 쓰나**: 재단 동기화에서 행마다 계산. `syncItems` 의 "바뀐 행만 갱신" 조건과 별개로 **전부 다시 계산**하고, 결과가 달라진 행만 쓴다 (규칙을 고치면 다음 동기화에 전부 반영되도록)
- **본문을 못 받았거나 추출이 실패해 모름이 되면 저장된 값을 유지한다.** 일정이 없어진 것이 아니라 읽지 못한 것이기 때문이다. 본문이 있는데 못 읽게 된 경우는 재단이 글을 바꾼 것이므로 지운다
- 영향 받는 조회: `EventResponse` 에 `scheduleStatus` · `scheduleText` · `scheduleHolidayNote` · `dates` 추가. `getAllEvents` 는 N+1(행마다 쿼리)을 피해 날짜를 한 번에 읽어 묶는다

## 6. 공휴일

| 표현 | 실데이터 | 달력이 없으면 생기는 일 | 방향 |
|---|---|---|---|
| 공휴일 **제외** (`월요일 및 공휴일 미운영`) | `시간` 칸 5건, 본문 추가 있음 | 평일 공휴일을 "진행"으로 안내 | **거짓 안내** (허탕 가능) |
| 공휴일 **추가** (`매주 금~일요일, 공휴일`) | idx 2970 | 평일 공휴일이 "진행"에서 빠짐 | 놓침 (허탕은 아님) |
| 예외 (`10월 5일의 경우 대체공휴일로 개관`) | idx 2984 | 월요일 휴관 규칙으로 빠짐 | 놓침 |

**결정: 처음에는 계산하지 않고 원문을 표시한다.** 날짜는 요일로만 펼치고, 원문에 `공휴일` 이 있으면 카드에 `공휴일 확인`(모바일 폭 때문에 줄임), 상세에 `공휴일은 원문 확인` 을 붙인다.
- 나중 선택지: 한국천문연구원 특일 정보 API 또는 연도별 공휴일 표를 도입해 제외 · 추가를 계산한다. 대체공휴일 · 임시공휴일 때문에 매년 갱신이 필요하므로, 실제로 틀린 안내가 문제 될 때 검토

## 7. 화면 · 기능

| 기능 | 내용 |
|---|---|
| 카드 · 상세 표시 | `DATES` 이고 날짜 5개 이하: `5/16 ~ 9/19 · 총 2회 · 5/16, 9/19`. 날짜가 많으면 요일로 요약 `5/1 ~ 11/1 · 금 · 토 · 일`, 상세에 전체 목록. `UNKNOWN`: 지금처럼 기간만 + 상세에 원문 |
| 요일 요약 조건 | 저장된 날짜에서 계산한다. 기간 안의 그 요일이 **빠짐없이** 있을 때만 `토요일만` 이라고 쓴다 (2972 같은 오안내 방지). 빠진 날이 있으면 `총 N회`. 4일 이상 이어지는 요일은 `화~일` 로 줄인다 (모바일 카드 폭) |
| "오늘 진행" 필터 | `DATES` 는 날짜 표에 오늘이 있을 때. `UNKNOWN` 이고 기간 안이면 **`기간 중 · 일정 확인` 표시와 함께 같이 보여 준다** (행사가 사라지지 않게 — 합치기와 같은 원칙) |
| "이번 주말" 필터 | 오늘 이후 가장 가까운 토 · 일 기준. `UNKNOWN` 처리는 위와 같음 |
| 캘린더 저장 | `DATES` 는 **날짜를 골라 1회 일정**으로 저장. 기본값은 오늘 이후 가장 가까운 날. `EventCalendarService` 에 날짜 인자를 추가하고, 그 날을 `timed()` 의 "하루짜리 행사"로 처리. `UID` 에 날짜를 넣음 (`event-{id}-{yyyymmdd}@…`). `UNKNOWN` · 날짜 지정 없음은 지금과 같음 |

- 여러 날을 한 번에 넣는 `.ics` `RDATE`(반복 날짜 항목)는 아이폰 · 구글 일정 추가 화면의 지원을 확인하지 못해 1차에서 뺀다
- 필터의 "오늘"은 **한국 시간** 기준으로 계산한다. 기존 `isPastEvent` 는 `toISOString()`(UTC, 세계 표준시)이라 오전 9시 전에는 전날로 계산되므로 그대로 복사하지 않는다

## 8. 합치기와의 관계

인스타끼리 묶이면 기간을 전부 덮는 글이 대표가 되어 안의 회차가 따로 안 보인다 (`docs/event-merge.md` 3번). 날짜 목록으로 회차를 다시 보여 줄 수 있다.

**결정: 저장은 행마다 그대로 두고, 대표의 날짜는 조회할 때 합친다.** `merged_into_id` 가 다시 계산되어도 날짜 표를 고칠 필요가 없다 (합치기 원칙 2번 "원본 보존").

| 대표 상태 | 대표 출처 | 화면 날짜 | 필터 판단 |
|---|---|---|---|
| `DATES` | 인스타 | 대표 ∪ 숨긴 행의 `DATES` | 합친 날짜 |
| `DATES` | 재단 | **재단 날짜만** (재단 우선 원칙) | 재단 날짜 |
| `UNKNOWN` | 무엇이든 | 대표는 기간 그대로, 숨긴 행 날짜는 **`확인된 회차` 로 표시만** | `UNKNOWN` 과 같음 |

- 3번 줄의 이유: 모음 글(`~12/31`)이 대표인데 숨긴 개별 글이 `11/1` 하루면, 합쳐서 `DATES` 로 만드는 순간 **"11/1 만 진행"으로 잘못 안내**한다. 숨긴 행의 날짜는 "이날은 한다"는 뜻이지 "다른 날은 안 한다"는 뜻이 아니다
- 합치기 기준 ① "날짜 겹침"은 **기간 그대로 유지**. 진행 날짜로 바꾸면 같은 전시의 다른 회차 글이 안 묶일 수 있고, 미리보기로 맞춘 결과(묶음 8 · 숨김 13)가 달라진다

## 9. 인스타

**제약 (기존 결정)**
- 캡션 원문은 저장하지 않는다 (`docs/instagram-integration.md` 8번) → 규칙을 고쳐도 DB 만으로 재처리할 수 없고 **게시물을 다시 받아야 한다**
- 계정당 최근 10개만 받는다 (`instagram.fetch-limit` 기본 10, 코드 상한 25). 동기화는 받아 온 글을 매번 다시 처리하므로 **창 안의 글은 다음 동기화 때 자동 재처리**된다. 창 밖의 글은 한도를 잠깐 올려 1회 수집하거나 포기한다 (오래된 글은 대부분 끝난 행사)

**`NO_DATE` · `PENDING` 살리기** — 마지막 실측은 PROGRESS 10/31 로그: `suwon_city` 블록 54개 중 `NO_DATE` 4 · `PENDING` 7, 다른 4계정 블록 44개 중 `NO_DATE` 2(연도 없음) · `PENDING` 29(라벨 줄 없음 26 · 장소 줄 없음 3). 이후 규칙이 바뀌었으므로 구현 전에 `BlockLog` 이유별로 다시 센다.

| 경우 | 지금 | 제안 |
|---|---|---|
| 기간 + 매주 (`2026. 5. 1.(금) ~ 11. 1.(일) 매주 금~일`) | 기간은 읽히지만 시간이 없으면 뒷부분을 버려 **요일이 사라짐** (`CaptionDateParser` `timeText`) | 뒷부분에서 요일을 읽어 날짜로 펼침 |
| 여러 회차 (`날짜가 여러 개`) | `PENDING` | 전부 읽어 시작일 = 최소, 종료일 = 최대, 나머지는 날짜 표. 모든 날짜가 요일 검사 통과할 때만 |
| `매주 금~일` 만 (기간 없음) | `NO_DATE` | **그대로 둠.** 기간을 지어내면 안 되고, `Event` 는 시작일이 있어야 지도에 의미가 있음 |
| `YYYY. M월` (일 없음) | `NO_DATE` | 그대로 둠 (`M월 전체`로 읽는 것은 추측) |
| 연도 없는 날짜 + 요일 (`11. 7.(토)`) | `NO_DATE` | 게시일 이후 요일이 맞는 가장 가까운 날로 읽을 수 있으나 **기존 "연도 추측 금지" 결정을 바꾸는 일** → 12번 결정 항목 |
| 라벨 줄 없음 (`PENDING` 대부분) | AI 몫 | 이 작업으로 해결 안 됨. AI 연결 뒤에 처리 |

**주의점**
- 블록 키가 바뀐다: 못 읽은 블록은 `원문 해시`, 읽으면 `제목 + 시작일 + 장소` (`BlockKeys`). 재처리하면 새 블록이 생기고 옛 `NO_DATE` · `PENDING` 행이 남아 **모음 글 판단이 틀어진다** (`docs/event-merge.md` 9번과 같은 문제) → **옛 블록 정리가 먼저**인 이유
- `ParsedEvent` 에 날짜 목록을 추가하고 `ParsedEventValidator` 가 4번 검사를 함께 하도록 한다. AI 경로도 같은 검사를 지난다
