# 같은 행사 합치기 — 설계 (초안)

> 인스타 연동 설계 문서 7번 #6 "중복" 의 구현 설계. 코드보다 먼저 **기준 · 데이터 모델 · 테스트**를 정한다.
> 관련: `docs/instagram-integration.md` 3-1 · 7번 #6 · #13, PROGRESS.md "같은 행사 합치기"

## 1. 문제

출처가 늘면서(재단 API + 인스타 5계정) **같은 행사가 여러 행으로** 들어온다.

| # | 경우 | 지금 화면에서 보이는 모습 |
|---|---|---|
| A | 재단 ↔ 인스타 (같은 공연을 재단 API · 인스타 둘 다 올림) | 재단 좌표(XML) ≠ 카카오 검색 좌표 → **가까운 자리에 마커 2개** |
| B | 인스타 모음 글 ↔ 개별 글 (월간 모음 + 공연 홍보 글) | 같은 장소명 → 같은 카카오 좌표 → 마커 1개지만 **목록에 같은 행사 2줄** |
| C | 인스타 계정끼리 (`suwon_city` · 시설 계정이 같은 공연을 올림) | B 와 같음 |
| D | 같은 계정 재게시 | B 와 같음 (게시물 id 가 달라 `sourceKey` 가 다름) |

- 화면(`index.html` `groupByLocation`)은 **좌표가 완전히 같을 때만** 한 마커로 묶음 → A 는 못 묶음
- 저장 단계의 중복 방지(`idx`, `(source, source_key)`)는 **같은 출처 · 같은 게시물 안**만 막음 → A~D 는 못 막음

## 2. 원칙

1. **틀리게 합치기 > 안 합치기 의 손해.** 다른 행사를 합치면 한 행사가 지도에서 사라짐. 애매하면 합치지 않는다 (마커 2개는 감수)
2. **원본 행은 지우지 않는다.** 숨김 표시만 → 재동기화해도 결과가 같고, 찜 연결이 끊기지 않음
3. **재단 데이터 우선** (인스타 설계 7번 #6 결정). 공식 · 정형 데이터라 날짜 · 장소가 더 정확
4. **매번 전체 다시 계산** (멱등 — 몇 번 돌려도 같은 결과). 행사 수가 수백 건이라 부담 없음

## 3. 합칠 기준

두 행사가 아래 **3가지를 모두** 만족하면 "같은 행사" 로 본다.

| 기준 | 같다고 보는 조건 | 이유 |
|---|---|---|
| ① 날짜 | 기간(시작~종료)이 **겹침**. 종료일이 없으면 시작일 하루로 봄. 둘 중 하나라도 시작일이 없으면 ❌ | 모음 글은 기간, 개별 글은 하루만 적는 경우가 있음 |
| ② 장소 | 좌표 거리 **300m 이내** 또는 정리한 장소명이 같음 | 재단 좌표 ↔ 카카오 좌표가 같은 건물이어도 조금 다름 |
| ③ 제목 | 정리한 제목이 같음 · 한쪽이 다른 쪽을 포함(짧은 쪽 4글자 이상, 숫자뿐이면 ❌) · 글자쌍 유사도 0.6 이상(같은 앞부분을 뺀 나머지도 0.6 이상, 나머지가 1글자 이하면 생략) | `2026 수원국악한마당` ↔ `<2026 수원 국악 한마당>` |

**제목 · 장소명 정리 규칙** (비교할 때만 씀, 저장값은 그대로)
- 공백 · 괄호류(`<> 〈〉 《》 「」 [] ()`) · 따옴표 · 이모지 · `#해시태그` 제거, 소문자. 태그를 빼면 숫자만 남는 제목(`2026 #뷰티썸수원`)은 태그 글자를 살림
- `&#39;` 같은 HTML 표기는 풀어서 비교 (나중에 할 일의 `&#39;` 항목과 무관하게 비교가 깨지지 않게)
- 글자쌍 유사도 = 두 제목을 2글자씩 잘라 겹치는 비율 (Dice 계수). 숫자는 정할 때 실데이터로 조정

**합치지 않는 경우 (테스트로 고정)**
- 같은 장소 · 같은 날 **다른 공연** (제목 ❌)
- 같은 제목 · **다른 회차 날짜** (날짜 ❌) — 회차마다 따로 보이는 게 맞음. 단 회차를 모두 덮는 글이 있으면 그 글이 대표가 되어 합쳐짐
- 같은 제목 · 같은 날 · **다른 장소** (순회 공연, 장소 ❌)

**묶음과 대표**
- 서로 같은 행사끼리 이어서 **한 묶음**으로 만듦 (A=B, B=C 면 A·B·C 한 묶음)
- 묶음 안 **대표 1개**만 지도에 보임. 우선순위: 재단(`SWCF`) → 인스타 개별 글(블록 1개짜리 게시물) → 인스타 모음 글 → 먼저 저장된 행(`id` 작은 쪽)
- **행사가 지도에서 사라지지 않게 하는 규칙** (2026-11-01, 사용자 결정). 화면은 대표 날짜로 지난 행사를 거르므로, 대표(11/1 하루) 뒤에 모음 글(~12/31)을 숨기면 남은 기간에 행사가 사라짐
  - 인스타끼리 묶이면 위 우선순위보다 **기간을 전부 덮는 행**이 먼저 대표가 됨 (여럿이면 그중 우선순위 순). 대가: 대표가 모음 글이면 이미지 · 링크가 덜 구체적이고, 안의 회차는 따로 보이지 않음 → 날짜 정제 작업에서 회차 표시 검토
  - 재단이 있으면 재단이 그대로 대표. 재단 기간을 벗어난 글, 전부 덮는 행이 없을 때 대표 기간을 벗어난 행은 숨기지 않고 그대로 둠 (마커 2개 감수)
- 묶음에 재단 행사가 **2개 이상** 끼면 합치지 않고 그 묶음 전체를 그대로 둠 (재단끼리는 원래 다른 행사 — 기준이 너무 느슨하다는 신호이므로 로그에 남김)

## 4. 데이터 모델 (V3)

| 안 | 방식 | 장점 | 단점 |
|---|---|---|---|
| **① 숨김 칸 (추천)** | `event.merged_into_id`(BIGINT NULL, 같은 표 FK). 대표는 NULL, 나머지는 대표 `id` | 원본 보존 · 재계산 쉬움 · 찜 유지 · 표 1개 칸 1개 | 조회마다 `merged_into_id IS NULL` 조건 필요 |
| ② 삭제 | 중복 행 삭제 | 조회 단순 | 다음 동기화 때 다시 생김 → 매번 삭제 반복, 찜 FK 충돌 |
| ③ 묶음 표 | `event_group` 표 + 연결 | 묶음 정보 풍부 | 지금 규모엔 과함 |

```sql
-- V3 (안 ①)
ALTER TABLE event ADD COLUMN merged_into_id BIGINT NULL;
ALTER TABLE event ADD CONSTRAINT fk_event_merged_into FOREIGN KEY (merged_into_id) REFERENCES event (id);
```

- 대표는 항상 **묶음 끝**을 가리킴 (A→B→C 같은 사슬 없음) → 화면 · 찜에서 한 번만 따라가면 됨
- 대표 행 자체의 정보는 바꾸지 않음 (인스타 링크를 대표 상세에 같이 보여주기는 8번 열린 결정)
- 숨김 해제: 다시 계산했을 때 묶음에서 빠지면 `merged_into_id = NULL` 로 되돌림 (예: 재단 행사가 사라짐)
- 대표 행이 지워질 때: FK 때문에 먼저 숨김 행의 `merged_into_id` 를 비운 뒤 지워야 함. 앱 코드에는 지우는 곳이 없고 `scripts/reset-instagram-dev.ps1` 이 인스타 행을 지움 → 3번 PR 전에 이 스크립트에 비우는 단계 추가. 앱 코드는 인스타 설계 7번 #13 `StaleBlockRetirer` 가 지우기 전에 비움

**영향 받는 조회**
| 위치 | 바꿀 점 |
|---|---|
| `EventService.getAllEvents` (`/api/events`) | 숨긴 행 제외 |
| `FavoriteService.getFavoriteEvents` | 숨긴 행을 찜했으면 **대표로 바꿔** 보여줌 (같은 대표가 겹치면 1개) |
| `FavoriteService.addFavorite` | 숨긴 행 id 로 찜하면 대표 id 로 저장 (화면엔 대표만 보이므로 드문 경우) |
| `FavoriteService.removeFavorite` | 대표 id 로 취소하면 **그 대표로 모이는 찜을 모두** 지움 (화면엔 대표 id 만 있어서, 숨긴 행을 찜한 경우에도 취소되어야 함) |
| 캘린더(`EventCalendarController`) | 숨긴 행 id 로 와도 그대로 동작 (원본 행이 남아 있음) → 변경 없음 |

## 5. 언제 실행하나

- `EventMergeService.recompute()` — 전체 행사를 읽어 묶음을 다시 계산하고 `merged_into_id` 를 갱신, 결과(묶음 수 · 숨긴 수 · 묶음별 제목 목록)를 돌려줌
- **재단 동기화(`/api/events/sync`) · 인스타 동기화(`/api/instagram/sync`) 끝에 자동 실행** (`EventMergeRunner`) → 재단은 응답 문구, 인스타는 JSON `merge` 칸에 개수 표시. 합치기가 실패해도 동기화는 이미 저장됐으므로 성공으로 응답하고 실패만 표시, 다음 동기화 때 처음부터 다시 계산. 재단 동기화가 중간 예외로 끝나도 앞 행들은 저장됐으므로 합치기를 실행하고 원래 실패를 돌려줌. 합치기는 한 번에 하나만 실행 (서버 1대 기준)
- 비교 수 줄이기: 시작일이 없는 행은 제외, 나머지는 날짜 겹침 먼저 확인 후 제목 · 장소 비교 (수백 건이면 전부 비교해도 1초 미만)
- **미리보기 먼저**: 자동 적용 전에 `GET /api/events/merge/preview`(저장 안 함)로 실데이터 결과를 눈으로 확인 → 기준 숫자(300m · 0.6) 조정 → 그다음 자동 실행 연결
- **모음 글 판단**: 행사로 읽힌 블록(`PARSED` · `NO_DATE` · `NO_COORD` · `ERROR` · `READY`)이 2개 이상인 게시물. 공지(`SKIPPED`) · 못 읽은 블록(`PENDING` · `FAILED`)은 세지 않음

## 8. 결정 (2026-11-01, 사용자)

1. **기준 엄격도** — **3가지 모두** 맞을 때만 합침. 실사용 피드백을 받아 기준 숫자 · 규칙을 조정
2. **데이터 방식** — 숨김 칸 `merged_into_id` (사용자 선호 없음 → 추천안)
3. **대표 상세에 인스타 원문 링크** — 나중에 (사용자 선호 없음 → 추천안, 이번 범위는 마커 정리만)

**1차 미리보기 결과 (2026-11-01, 임시 DB · 재단 118 + 인스타 READY 45)**: 묶음 8 · 숨김 13 · 충돌 4. 잘못 합쳐진 묶음 없음 → 기준 숫자 유지
- 충돌 4건은 모두 재단 행사끼리 겹친 쌍 → 합치지 않음. 이 중 `정조테마공연장 2026 작은 음악회` ↔ `마당놀이터`(유사도 0.67)는 다른 행사 → 시설명이 제목 앞에 붙으면 유사도가 부풀려짐 → 같은 앞부분을 뺀 나머지도 비교하도록 규칙 추가
- 규칙 추가 후 같은 데이터로 재확인: 묶음 8 · 숨김 13 그대로, 충돌 4 → 3 (`작은 음악회` ↔ `마당놀이터` 가 빠짐), 대표 기간을 벗어난 숨김 0
- 안 합쳐진 중복 후보: `수미C의 성덕일지 10월 프로그램` ↔ `<내 고민을 콘텐츠로 만드는 방법>`(같은 날 · 같은 자리, 유사도 0.55). 원칙 1번대로 그대로 둠

**피드백 반영 방법**: 3번 PR 의 미리보기 결과 + 실제 화면에서 "안 합쳐진 중복" · "잘못 합쳐진 쌍"을 PROGRESS.md "나중에 할 일"에 기록 → 기준 숫자(300m · 0.6 · 4글자)만 바꾸는 작은 PR 로 조정
